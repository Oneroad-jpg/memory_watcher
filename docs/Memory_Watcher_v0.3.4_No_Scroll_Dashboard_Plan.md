# Memory Watcher v0.3.4 スクロール不要ダッシュボード工程表

## 0. 文書の位置付け

本書は、Memory Watcherの主要情報をスクロールせず一画面で確認できるようにする
独立工程です。工程番号は**工程25**、対象versionは**v0.3.4**とします。

現在の状態は**工程表作成済み・実装未着手**です。本書のチェック項目や試験は、
実際に観測するまで合格扱いにしません。本書が`main`へ保存されても、工程25の
実装、検証、署名、公証、公開が完了したことにはなりません。

前提となる公開版はv0.3.3です。メモリ・CPUの測定、SQLite、履歴期間、
表示構成エディタ、Developer ID署名・公証済み配布を土台として使用します。

## 1. 目的

標準ウインドウを開いたとき、次の情報へ縦・横スクロールなしで到達できるようにします。

- 現在のメモリ、Mac全体CPU、Pressure、監視状態
- メモリ構成、スワップ、Pressureの履歴
- Mac全体CPUの履歴
- すべての論理CPUの現在値と履歴
- 12時間・24時間・3日の期間切替
- 更新、表示設定、ログイン時起動
- 選択した時刻のメモリ・CPU詳細

「すべてを表示するため文字やグラフを判読不能な大きさまで縮める」のではなく、
情報の種類に応じて小型履歴、ヒートマップ、オーバーレイを使い分けます。

## 2. 「スクロール不要」の定義

工程25でいうスクロール不要は、次の全条件を満たす状態です。

| 条件 | 合格基準 |
|---|---|
| 対象画面 | 通常のMemory Watcherダッシュボード。表示設定sheetは別に扱う |
| 対象サイズ | content areaが1,024×720、1,080×900、1,440×900 points |
| 対象CPU数 | 1・8・16・32論理CPU |
| 対象設定 | すべてのセクションを表示する標準設定。利用者が任意に隠した項目は欠落と数えない |
| 縦スクロール | ホイール、トラックパッド、Page Downを使わず主要情報が見える |
| 横スクロール | 横移動なし。グラフ・操作・CPU番号が切れない |
| 到達可能性 | 必須項目の表示frameがcontent area内にあり、隠れた必須項目が0件 |
| CPU完全性 | 期待するCPU indexの集合と表示したCPU indexの集合が一致する |
| 読みやすさ | 単位、状態名、CPU番号、主要数値を判読でき、文字を省略しない |

1,024×720 points未満へウインドウを縮めた場合は、内容を隠すのではなく、
検証済み最小サイズをウインドウの下限として維持します。

32を超える論理CPUは一画面保証の対象外です。ただし値を捨てず、32件単位の
ページ切替で全CPUへ到達できる設計とし、未検証範囲として表示します。

## 3. 変更する範囲・変更しない範囲

### 変更する範囲

- 上部ヘッダーの高さと情報配置
- 履歴領域の固定グリッドと高さ計算
- 論理CPU数に応じた小型履歴・ヒートマップ切替
- 選択時刻詳細のオーバーレイ表示
- ダッシュボードの最小ウインドウサイズ
- 表示構成設定と新しい一画面配置の整合
- 一画面表示の自動試験と実機確認

### 変更しない範囲

- 5秒の測定周期
- メモリ・CPUの取得元、計算式、単位
- SQLite schema、保存場所、12時間・24時間・3日の保持
- sleep、gap、UNKNOWN、取得不能、再起動の意味
- メニューバー常駐とログイン時起動の仕組み
- 通信なし、通知なし、クラウド同期なしという境界
- GPU、プロセス別・アプリ別解析、AI診断

表示を一画面へ収めるために、保存値の削除、CPU系列の平均化、欠測の補間、
UNKNOWNの0%変換は行いません。

## 4. 予定する画面構成

```text
┌──────────────────────────────────────────────────────────────┐
│ 現在値・監視状態・Pressure・期間・更新・表示設定・ログイン時起動 │
├────────────────────────────────┬─────────────────────────────┤
│ メモリ構成の履歴               │ 全論理CPUの履歴             │
│                                │ 1〜8 CPU: 小型履歴           │
│ スワップ                       │ 9〜32 CPU: ヒートマップ      │
│ Pressure                       │                             │
│ Mac全体CPU                     │ 全CPUの現在値               │
├────────────────────────────────┴─────────────────────────────┤
│ 選択時刻の要約。操作時は同じ画面内に詳細表を重ねて表示          │
└──────────────────────────────────────────────────────────────┘
```

### 論理CPU数ごとの表示

| 論理CPU数 | 表示方法 | 完了条件 |
|---:|---|---|
| 1〜8 | CPUごとの小型折れ線グラフ | 全CPUを同時表示し、CPU番号、現在値、UNKNOWNを区別する |
| 9〜32 | CPUを行、時刻を列、使用率を色とするヒートマップ | 全CPU indexを省略せず、sleep・gap・UNKNOWNを空白または専用表現で区別する |
| 33以上 | 32CPU単位のページ切替 | 値を削除せず、現在ページと総ページ数を示す。一画面同時表示は未検証と明記する |

ヒートマップはCPUをまとめた平均値ではありません。各行が保存された1つの論理CPUに
対応し、時刻方向の描画点を減らす場合もgapの両側を接続しません。

### 選択時刻の詳細

- 通常時は1行の要約だけを表示する
- グラフ選択またはキーボード操作で、同じウインドウ内に詳細表を重ねる
- メモリ、Pressure、CPU全体、user・system・nice・idleを表示する
- 1〜32 CPUは4列または8列の表でスクロールせず全値を表示する
- 未測定値を別の時刻や別のCPUから補わない
- Escape、閉じるボタン、VoiceOver操作で元の一覧へ戻れる

## 7. 完了判定の測定方法

### 7.1 一画面表示

各fixtureで必須要素へ識別子を付け、表示frameがcontent areaと交差するだけでなく、
全体が範囲内にあることを機械判定します。CPUは表示したindexを集合として比較し、
件数だけ合って番号が入れ替わる不具合も失敗にします。

rootに縦・横の`NSScrollView`が存在しないこと、ホイール操作前後で表示原点が
変わらないことを確認します。オーバーレイを開く操作はスクロールとは扱いませんが、
1〜32 CPUの詳細自体もスクロールなしを要求します。

### 7.2 読みやすさ

- CPU番号、状態、単位、主要数値へ省略記号を出さない
- Pressure、UNKNOWN、sleep、gapを色だけで区別しない
- グラフを縮めても選択時刻の元記録を詳細表から確認できる
- 模擬データの画面と実測画面を明確に区別する
- light・darkの両方で文字と背景のコントラストを確認する

### 7.3 性能

過去の工程と同じく、現在値更新だけで履歴全体を再描画・再読込みしない構造を
維持します。最も重い3日・32 CPU条件で、表示開始から操作可能になるまでを3回測り、
最速値ではなく最大値が2秒以内であることを要求します。

表示・非表示それぞれ30分について、累積CPU時間差を経過時間で割った平均CPUを
測定します。短時間試験から24時間のリーク不存在を断定せず、既存の長時間監査結果と
今回のRSS推移を別々の証拠として残します。

工程25は表示層だけの変更として計画しているため、新しい24時間監査は完了条件へ
追加しません。測定エンジン、SQLite schema、保持処理へ変更が及んだ場合は表示層だけの
工程ではなくなるためHOLDとし、24時間監査を含む別工程が必要か再判定します。

## 9. 停止規則

次のいずれかが発生した場合は、その時点で変更、commit、PR、merge、署名、公証、
インストール、Release公開を停止し、原因と証拠を報告します。

- 必須情報の欠落、表示の重なり、判読不能、スクロールの再発
- CPU indexの欠落・重複・取り違え
- sleep・gap・UNKNOWN・取得不能の偽装または補間
- 測定周期、計算式、SQLite schema、保持期間の意図しない変更
- 初期表示2秒超過、平均CPU 1%以上、RSS単調増加
- 説明不能な測定欠落、SQLite不整合、Internet socket検出
- 通信・通知API、認証情報、端末固有path、非公開ログの混入
- テスト、build、format lint、署名、公証、Gatekeeperの失敗

単に表示を収めるため、閾値を緩めたり、CPUを間引いたり、機能を非表示にして
合格扱いにしません。複雑なincidentは原因を確定できる状態を保存してHOLDとし、
別の変更を混ぜません。

## 10. GitHub保存規則

この工程表の文書PRは、工程25の実装より先に計画を固定するためのものです。
文書PRのmergeは実装完了を意味しません。

実装は、文書PR merge後の`main`から新しい`phase/25-no-scroll-dashboard` branchを
作成して開始します。工程25の実装、試験、検証記録、version更新はちょうど1個の
非merge commitへまとめ、ready PR、merge commit、remote readbackの順で保存します。

配布ZIP、実機固有ログ、監査の生記録、認証情報はGit履歴へ含めません。Releaseには
公開用ZIPと利用者向けRelease Notesだけを添付し、公開後のZIPを別の一時領域へ
再ダウンロードして検証します。

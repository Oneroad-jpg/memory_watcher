## 2. 画面とデータの固定条件

| 項目 | 実装する挙動 | 合格の判定基準 |
|---|---|---|
| ウインドウ | メニューバーから1つの統合ウインドウを開く | 繰り返し操作しても同じウインドウを再利用し、CPU専用の別窓を作らない |
| 配置 | 上部に現在値・論理CPUメーター・共通操作、左に論理CPU履歴、右にメモリ・スワップ・Pressure・CPU全体履歴 | 狭い幅では縦並び。縦スクロールは許可するが、機能を別ウインドウや別アプリへ追い出さない |
| 期間 | 12時間・24時間・3日 | 全履歴が同じ開始・終了UTCを持つ。7日・30日の操作を残さない |
| 保存層 | 12時間・24時間は5秒生データ、3日は1分集約 | UI都合で測定を追加したり、SQLiteの保持期限を延長したりしない |
| 現在値 | 最後に正常取得したメモリ値とCPU区間平均 | 「現在」と最終測定時刻を表示。過去時刻を選んでも現在値欄を置き換えない |
| CPUの尺度 | CPU全体も各論理CPUも0〜100% | 工程13の正規化定義を使う。全体値を各CPUの単純合計として表示しない |
| CPUの名前 | 保存されたindexと対応する中立な番号 | 再起動・トポロジー境界も識別する。根拠のない高性能・高効率の名前を付けない |
| 不明・欠測 | UNKNOWN、未測定、取得エラーを値と分ける | 不明を0%に変換しない。正常な0%は0%として表示する |
| 古い現在値 | 最終値と古い状態を明示 | 15秒以上新しい正常値がない場合は「更新待ち／最終値」。sleep・停止を検知した場合はその時点で現在値扱いを解除する |
| 時間の表示 | 内部照合はUTC、画面は利用者のローカル時刻 | 詳細欄で実測時刻・CPU測定区間・集約区間を確認できる。時計変更前後を同一連続系列へ接続しない |
| 自動更新 | 現在値は5秒測定に追従、履歴の自動再読込みは最短5分 | 現在値更新だけで履歴全体を読まない。非表示・最小化中は新たな自動履歴読込みを開始しない |
| 手動操作 | 期間切替・更新ボタン・ウインドウ再表示で必要な履歴を読む | 最新の操作だけを採用する。操作応答と読込み中表示は1秒以内、表示完成の性能は後述の試験で判定する |

UNKNOWNや更新待ちの文字はアプリ内の状態表示であり、OS通知を追加するものではない。

### 16A-2. 表示用データモデルの分離

### 16A-4. 共通期間と非同期読込みの制御

**成果物:** 共通期間コントローラー、世代管理、遅延・逆順応答のテスト。

**完了条件:** 期間を連続10回切り替えても最後の選択だけが採用される。
一部パネルだけ旧期間の値を見せない。読込み失敗は無限再試行せず表示する。
T07・T08がPASS。

**成果物:** 現在値パネル、論理CPU別メーター、古さ判定のテスト。

### 16A-6. メモリ・CPU履歴の統合

捏造しない。T11・T12がPASS。

### 16A-7. 共通の時刻選択と値の照合

**入力:** 選択UTC、元記録、連続区間、各CPU測定区間・集約区間。

**作業:** どの履歴を選択しても、全履歴が同じ選択UTCを参照するようにする。
各指標は下記の照合規則で検索し、実測時刻や区間の違いを詳細欄に残す。

**成果物:** 共通カーソル、詳細欄、境界時刻・欠測時刻の照合テスト。

**完了条件:** 同じ時刻を指しているように見せるための補間をしない。
時刻選択でSQLite全件を再読込みしない。選択を動かしても現在値欄は現在値のまま。
T13・T14がPASS。

照合規則は次のとおりとする。

- 生のメモリ値: 選択UTC以前の最新サンプルを使う。ただし差が5秒以内で、
  その間にgap・sleep・時計変更・再起動境界がない場合だけ採用する。
- 生のCPU値: 選択UTC以前に測定が完了した最新の区間平均を使う。
  区間終了から選択UTCまで5秒以内であり、欠測をまたぐ無効な測定ではないこと。
- 1分集約: 選択UTCを含む区間 `[開始UTC, 終了UTC)` を使う。
  終了UTCがスナップショットの終了を越える未完了区間は採用しない。
  選択UTC自体がsleepや記録されたgap内なら、平均値が存在しても未測定とする。
- 条件を満たす記録がない指標は「この時刻は未測定」とする。他の指標の時刻へ
  ずらして値を埋めない。集約値には元の実測件数と集約区間を表示する。

### 16A-8. sleep・復帰・再起動・エラーの状態遷移

**完了条件:** 復帰時のCPU初回値を工程13の規則どおりUNKNOWNで扱える。

同番号へ誤接続しない。T15・T16がPASS。

## 5. 性能・正確さの測定方法

### 5.1 初期表示時間（T19）

1. 対象Macの論理CPU数に合わせた隔離fixtureを作る。メモリと全CPUに3日分の
   1分集約、直近24時間に5秒データを配置し、sleep・gapも含める。
2. Release版を使用し、通常の実測DBとfixtureを混ぜない。模擬データの画面は
   検証用だと識別できるようにする。
3. 各期間についてアプリを起動し直し、3回ずつ測定する。OSキャッシュの強制削除はしない。
4. 計測開始は統合ウインドウの表示要求時、終了は要求期間のデータが確定し、
   可視領域のグラフが最初に描画され、操作可能になった時点とする。
   SQLite読込み完了だけを画面完成時刻にしない。
5. 9回の生の所要時間と最大値を残す。全9回が2秒以内でPASS。

### 5.2 CPU負荷・記録継続（T21）

1. T19で初期表示所要時間が最大だった期間を使う。全論理CPUを持つfixtureで負荷を検証し、
   実記録の正確さはT22・T23で別に確認する。
2. 初回表示後の60秒を準備時間とし、その後15分を表示条件として測定する。
   次にウインドウを非表示にし、開始済み読込みの終了を確認してから15分測定する。
3. 各条件の0・5・10・15分に累積CPU時間、単調時計、RSS、記録時刻・件数を記録する。
   sleepや対象PID変更で条件が崩れた場合は有効な試験として扱わず、理由を報告して停止する。
4. 平均CPUは `100 × (終了時の累積CPU秒 − 開始時の累積CPU秒) ÷ 経過秒` とする。
   アプリ自身の全スレッド合計であり、論理CPU数では割らない。
5. 各15分区間が1%未満ならCPU条件PASS。履歴の定期更新を測定区間から除外しない。
6. 5秒記録を前工程で固定した遅延・gap規則で検証し、説明不能な欠落0件を要求する。
   RSSは全観測値を残す。短時間でリークなしと断定せず、24時間の増加傾向は工程17で判定する。

### 5.3 表示値の照合（T22）

- 内部表示モデルは、採用したSQLite記録と同じ値・時刻・品質を持つこと。
- GBは `bytes ÷ 1,000,000,000`、小数点以下2桁表示とする。
  文字列照合の丸め許容差は0.005GB以内。GiBへの無断変更はしない。
- CPUは小数点以下1桁表示とし、丸め許容差は0.05パーセントポイント以内。
  この許容差を計測式の不一致や異なる測定区間の説明に流用しない。
- 集約は採用区間と実測件数も一致すること。採用条件が満たせない場合の正解は未測定である。
- 表示期間に実測が不足する場合は件数と不足期間を記録する。3日分の実測完了を
  主張するために模擬データを足したり、別の24時間監査を追加したりしない。

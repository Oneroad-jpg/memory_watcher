# Memory Watcher 2層3セクション設計方針

この文書は、Memory Watcherの機能を安全に分割するための公開設計方針です。
個別機能の完成、将来版の実装、配布準備の完了を示すものではありません。

## 構造

各機能領域は、意味と実現処理を混在させないため、次の2層3セクションとして
整理します。

```text
機能領域
├── Meaning Layer
│   ├── API Section
│   └── Meaning Section
└── Support Layer
```

### Meaning Section

その機能で使う値、状態、制約、状態遷移を定義します。

- 値や状態が何を意味するかを所有する
- 成立しない組合せや範囲外の値を拒否する
- 情報不足を推測値へ置き換えない
- OS、データベース、画面部品などの実装詳細を持たない

### API Section

機能領域へ入る情報と、外へ出せる情報の境界を定義します。

- 入出力の型とversionを固定する
- 入力条件を満たした情報だけをMeaning Sectionへ渡す
- 検証済みの結果だけを外部へ返す
- 不正な経路、欠落、不整合を成功として扱わない

API Sectionは単なる通信処理ではありません。意味を持つ情報が境界を越えてよいかを
管理するため、Meaning Layerに属します。

### Support Layer

macOS、SQLite、SwiftUIなど、実際の環境と接続する処理を担当します。

- OSから観測値を取得する
- データを保存・読出しする
- 画面へ表示する
- 実行失敗をエラーまたは不明状態として返す

Support Layerは、Meaning Sectionで定義されていない意味や状態を独自に作りません。

## 情報の流れ

外部から取得した情報は、API Sectionの検証を通過してからMeaning Sectionへ渡します。
Meaning Sectionが生成した結果も、API Sectionから公開可能な型として取り出します。

```text
外部環境
  -> Support Layer
  -> API Section（入力検証）
  -> Meaning Section（意味と状態）
  -> API Section（出力検証）
  -> Support Layer
  -> 保存または表示
```

この経路により、OS API、保存方式、画面構成を変更しても、値や状態の意味を維持しやすく
なります。

## 適用方法

2層3セクションは責務の境界です。すべての機能を三つの独立したSwift Package targetへ
分割することを要求しません。

- 外部接続や状態判断が複雑な領域では、moduleやtargetでも依存を分離する
- 小さな領域では、file、型、testによる分離から始める
- 実装が存在しない領域には、完成しているように見える空のsourceを作らない
- 分離のためだけに動作や保存形式を変更しない

境界が有効かどうかは、フォルダ名ではなく次の性質で確認します。

- Support実装を交換してもMeaning Sectionの定義を変更せずに済む
- 不正な入力をAPI Sectionで拒否できる
- 意味のtestをOSや画面から独立して実行できる
- 実装詳細がMeaning Layerへ逆流しない

## 現行版との関係

この方針は段階的に適用します。既存sourceの配置だけを根拠に、すべての境界が実装済み、
検証済みであるとは扱いません。

設計上の分離、source上の分離、test、build、配布はそれぞれ別の確認事項です。
各変更は既存の測定値、SQLite記録、画面表示との互換性を確認しながら進めます。

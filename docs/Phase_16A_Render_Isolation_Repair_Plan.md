# 工程16A-R 履歴Charts描画分離・CPU HOLD修復工程表

## 0. 位置付けと現在状態

本書は、工程16Aの必須試験T21で平均CPU 1%未満を安定して満たせなかった場合に、
現在値表示の更新が履歴Chartsの描画へ波及しない構造へ修復するための工程表である。
工程16A-Rは独立した公開工程ではなく、工程16A-10「負荷抑制と性能測定」の
HOLD解消作業である。

- 現在状態: **CPU性能条件HOLD・修復計画作成済み・完了未判定**
- 目的: 5秒測定に追従する現在値と、低頻度で更新する履歴Chartsの描画責務を分離する。
- 維持する条件: 単一ウインドウ、単一監視エンジン、5秒測定、12時間・24時間・3日履歴。
- 対象外: CPU計算式、SQLiteスキーマ、保持期限、GPU、プロセス別解析、通知、通信。
- 合格条件は変更しない。T21の各15分区間で平均CPU 1%未満を要求する。
- 短時間の改善値、画面の見た目、テストPASSだけでHOLDを解除しない。

本書の作成は実装完了、HOLD解除、コミット、PR、マージを意味しない。
修復コードと本書は、工程16Aの全受入条件がPASSした後の単一コミットへ含める。

## 1. 固定する設計境界

### 1.1 単一ウインドウ内の独立描画ルート

統合ウインドウは1個のまま、次の2つを別々のSwiftUI描画ルートとして保持する。

1. **現在値ルート**
   - 監視状態、記録件数、Pressure、メモリ現在値、CPU全体、論理CPU別メーターを表示する。
   - 最新測定を受けて最大1秒以内に更新する。
   - 履歴スナップショット、Charts、期間別配列を入力に持たない。
2. **履歴ルート**
   - 期間操作、メモリ・スワップ・Pressure・CPU履歴、時刻選択、詳細欄を表示する。
   - 履歴スナップショット、期間、選択UTC、読込み状態だけを入力に持つ。
   - 現在値revision、現在時刻の周期更新、論理CPUの最新値を監視しない。

2つのルートは、同一`NSWindow`内の固定したAppKitコンテナへ別々の
`NSHostingView`または`NSHostingController`として載せる。現在値の文字列やバー幅が
変化しても履歴ルートのroot view、Charts入力、ウインドウの最小・最大サイズを
再設定しない。別ウインドウ、別プロセス、2個目の監視エンジンは作らない。

### 1.2 状態の所有権

| 状態 | 所有する側 | 更新契機 | 禁止する依存 |
|---|---|---|---|
| 現在のメモリ・CPU・Pressure | 現在値専用store | 5秒測定、Pressure変化、life cycle | 履歴スナップショット、期間、選択UTC |
| 監視状態・記録件数 | 現在値専用store | start、stop、sample、failure | Charts、履歴配列 |
| 履歴スナップショット | 履歴専用store | 初回、手動更新、期間変更、表示中の5分更新 | 現在値revision、1秒・5秒の時計更新 |
| 選択UTC・詳細 | 履歴専用store | 利用者の履歴操作 | 現在値の置換、SQLite再読込み |
| ウインドウ表示状態 | window controller | 開く、閉じる、最小化、復帰 | 監視エンジンの再生成 |

現在値と履歴の双方から参照できるのは、値を持たない固定定義と表示書式だけとする。
1つの`ObservableObject`を両描画ルートから観測しない。

## 2. 固定進行順

進行順は次のとおりとし、前工程がPASSするまで次工程へ進まない。

`R0 証拠固定 → R1 計測器 → R2 状態分離 → R3 描画ルート分離 → R4 現在値軽量化 → R5 履歴隔離 → R6 状態遷移 → R7 自動試験 → R8 予備性能判定 → R9 正式T21 → R10 最終検証・マージ`

## 5. CPU測定と証拠の固定方法

平均CPUは工程16AのT21と同じ式を使う。

`100 × (終了時累積CPU秒 − 開始時累積CPU秒) ÷ 単調時計の経過秒`

- アプリの全スレッド合計とし、論理CPU数で割らない。
- 起動直後の60秒だけを準備時間として除外する。
- 履歴の5分自動更新、通常の5秒測定、画面描画を測定から除外しない。
- PID変更、sleep、対象ウインドウ条件の崩れがあれば、その測定は無効として停止する。
- 最短区間だけ、最も良い区間だけ、瞬間`%CPU`だけを採用しない。
- 公開文書には判定、式、条件、集約値だけを載せる。PID、ローカルパス、端末固有ログ、
  生のsample・traceは非公開検証証拠として分離する。

## 6. HOLD・再開・ロールバック規則

次のいずれかを検出した時点で、その工程をHOLDし、追加修正、監査再開始、commit、PR、
mergeを停止する。

- R2〜R5で現在値と履歴の依存が残る。
- 現在値反映が1秒を超える、または表示値・UNKNOWNの意味が変わる。
- 5分予備判定または正式T21で平均CPUが1%以上になる。
- 説明不能な測定欠落、PID変更、SQLite不整合、Internet socketを検出する。
- 既存メモリ・CPU・sleep・期間・時刻選択試験が退行する。
- 公開差分から認証情報、ローカルパス、非公開ログ、内部実行手段の名称を検出する。

HOLD時は、原因が特定できている変更だけを候補として保持する。閾値を緩めず、
失敗した監査をPASSへ書き換えない。複数案の先回り実装や、別incidentの修正を混ぜない。

ownerが文書レビュー用PRを明示的に要求した場合に限り、HOLD中でも次の条件で
**文書専用Draft PR**を作成できる。

- `origin/main`から隔離したブランチを使い、修復計画文書以外を含めない。
- PRをDraftのまま保持し、ready化・merge・工程完了判定を行わない。
- HOLD中の実装ブランチ、非公開監査ログ、端末固有情報を混ぜない。
- 最終工程16A PRの前にcloseまたは置換し、別マージとして履歴へ入れない。

この例外は文書レビュー経路だけを開く。実装再開、性能PASS、HOLD解除、最終commitの
権限を与えない。

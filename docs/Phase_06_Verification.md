# 工程6 常時監視とライフサイクル 検証記録

## 実装範囲

- アプリ起動時に直ちに1回測定し、以後5秒間隔で測定する監視エンジン
- ウインドウとは独立したアプリケーションコーディネータによる監視寿命管理
- sleep前のタイマー停止、wake直後の測定再開、時計変更の記録
- 前回保存したシステム稼働時間との比較による再起動の識別
- メモリ測定値、取得gap、プレッシャー状態、ライフサイクル事象の逐次保存
- `SMAppService.mainApp` を使ったログイン時起動の有効・無効切替
- OSの承認が必要な状態を `requiresApproval` として区別する表示

通知、外向き通信、クラウド保存、プロセス別解析は追加していません。

## スキーマversion 2

工程5のversion 1を保持したまま、次のテーブルを取引内の移行で追加しました。

| テーブル | 内容 |
|---|---|
| `system_lifecycle_events` | `LAUNCH`・`SLEEP`・`WAKE`・`CLOCK_CHANGED`・`REBOOT_DETECTED` |

各事象はUTC時刻とシステム稼働時間を持ちます。sleepからwakeまでの区間には
測定値を生成しません。工程8のグラフはこの区間を線で補間せず空白として
扱えます。

再起動は、起動時の稼働時間が直前に保存された測定値の稼働時間より小さい
場合だけ識別します。比較元がない初回起動では推測しません。時計変更は、
連続する測定のUTC経過時間と稼働時間の差が2秒を超えた場合、またはOSの
時計変更通知を受けた場合に記録します。

## 完了条件と結果

| 完了条件 | 検証結果 |
|---|---|
| 起動中に5秒間隔で測定する | 起動直後の即時測定と5秒タイマーを実装。署名済みアプリで6.5秒後に2件を確認 |
| ウインドウを閉じても測定が続く | 実アプリのウインドウを閉じ、画面非表示のまま監視状態 `running`、測定2件を確認 |
| ログイン時起動を有効・無効にできる | `/Applications` に一時配置した署名済みアプリで、`notRegistered → enabled → notRegistered` を実機読戻し |
| sleep中に偽の測定値を生成しない | エンジン試験でsleep後にタイマー停止、追加測定0、`SLEEP` 保存を確認 |
| wake後に測定を再開する | エンジン試験で `WAKE` 保存、直後の1件測定、5秒タイマー再設定を確認 |
| sleep区間を保持する | `SLEEP` と `WAKE` を独立した時刻付き事象としてversion 2 DBへ保存・読戻し |
| 時計変更を識別する | UTC経過時間と稼働時間の差、およびOS時計変更通知の経路を実装し、保存を試験 |
| 再起動を識別する | 前回測定より小さい起動時稼働時間でのみ `REBOOT_DETECTED` を保存する試験に合格 |
| 並行動作で競合しない | 監視エンジン5試験がThread Sanitizer付きで合格、警告0 |
| 全ビルド・全単体テストが成功する | debug/release build、Swift format lint、全38テストに合格 |

## 署名済みアプリの読戻し

通常起動スモークではbundle identifier
`com.oneroad.memorywatcher`、表示ウインドウ1、監視状態 `running`、
初回測定1件を読み戻しました。

ログイン時起動は、開発用ビルド位置ではOSがサービスを見つけられず
`notFound` になるため、署名済みの同一アプリを一時的に
`/Applications` へ置いて検証しました。最初の登録で
`notFound → enabled → notRegistered`、再試験で
`notRegistered → enabled → notRegistered` を確認しました。
検証後、一時アプリは `/Applications` から撤去し、ログイン項目も
`notRegistered` のままです。

## 検証境界

sleep・wake・時計変更・再起動の状態遷移は、OS通知と同じ入口を使う
決定論的テストで検証しました。実際の24時間運転、実機sleep・wake、
再起動後の読戻しは工程10の実運転で最終確認します。ここでは実施済みだと
扱いません。

## 判定

工程6の常時監視、閉窓後の継続、ログイン時起動、ライフサイクル識別、
sleep区間を偽データで埋めない条件を満たしました。履歴の集約と保存期限は
工程7で実装します。
